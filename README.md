# codex-subagent-routing

Codex アプリのサブエージェントを「安いモデルから始め、必要なときだけ昇格する」ように制御する AGENTS.md 規範です。
コードやプラグインではなく、`~/.codex/AGENTS.md` に貼る文章1節と、効いているかを確かめる監査スクリプトの2点で構成します。

## 何が起きるか

- サブエージェント起動時に必ずモデルと推論強度を明示させる（親設定の暗黙継承を禁止）
- 起動直前に `routing: <タスク> → <モデル>/<effort> — <理由>` を1行出させる（後から監査できる）
- 親（オーケストレーター）と子のモデルを分ける。親は `gpt-6-astra`、子は `gpt-5.6-terra` / `gpt-5.6-sol` の2モデルのみ（子に親と同格のモデルを指定しない）
- モデルと推論強度を別々に選ばせる。推論強度は medium → high → xhigh の順に上げ、モデル昇格（terra → sol）は推論強度を上げても受入基準が未達と証跡で確認できた時だけ
- 失敗時だけ上位モデルへ昇格し、解決したら元に戻す（昇格が粘着しない）
- 最上位の推論強度（ultra）は sol 限定で、単発の高リスク判断と最終ゲートに限定する
- 完了報告の前に、実装者とは別の検収専用サブエージェントを必ず1本立てる

## 前提条件（必読）

1. **Codex 0.150 以降が必要です**（アプリは同梱、CLI は `npm i -g @openai/codex@latest`）。0.149 以前の CLI では `spawn_agent` にモデル引数が無く、宣言文だけ残って子は親のモデルを継承します。`codex --version` で確認してください。
2. モデル名は作成者の契約で使える `gpt-6-astra`（親）/ `gpt-5.6-terra` / `gpt-5.6-sol`（子）で書いてあります。自分のプランで使えるモデルに合わせて置換してください（下表）。`gpt-6-astra` は CLI 0.153 以降が必要です（0.152 では 400 で拒否されます）。
3. 検収済みの文言です。特にルール6〜8と「推論強度の選択基準」は表現を削ると抜け道ができるので、モデル名以外は改変しないことを勧めます。

## 導入（4手順）

1. `ROUTING.md` 内のモデル名を自分のプランに合わせて置換する（下表）
2. 置換済みの `ROUTING.md` の内容を `~/.codex/AGENTS.md` の末尾に追記する（ファイルが無ければ新規作成）
3. `~/.codex/config.toml` に子エージェントの既定モデルを設定する（`config.snippet.toml` の内容。規範が指定を漏らしたときの床になります）。既に `[agents]` セクションがある場合はテーブルを重複させず、その中に2キーを追加する（重複テーブルは TOML 解析エラーになります）。`codex --strict-config exec --help` が通れば構文は正常です
4. サブエージェントを使うタスクを数回走らせ、このディレクトリで `python3 audit.py` を実行して明示指定率を確認する

規範（手順2）と既定値（手順3）は役割が違います。規範はタスクに応じて昇格・降格を判断させるもの、既定値は指定が無かったときに上位モデルへ落ちないための安全網です。両方入れてください。

## モデル名の置換表

| 文中の表記 | 意味 | 置換先の目安 |
|---|---|---|
| `gpt-6-astra` | 親（オーケストレーター）。config.toml の既定モデル | 自分のプランで最も強いモデル。子には指定しない |
| `gpt-5.6-terra` | 安価・標準の作業モデル（子） | 自分のプランで最も安く常用できるモデル |
| `gpt-5.6-sol` | 上位モデル（子の昇格先） | 自分のプランで2番目に強いモデル。親と同じでも可 |
| `medium` / `high` / `xhigh` / `ultra` | 推論強度（Codex の reasoning_effort） | 通常はそのまま。xhigh / ultra が無いプランなら最上位に読み替え |

置換箇所は `rg -o 'gpt-6-astra' ROUTING.md | wc -l`（2）、`rg -o 'gpt-5.6-terra' ROUTING.md | wc -l`（4）、`rg -o 'gpt-5.6-sol' ROUTING.md | wc -l`（7）で確認できます。

## 監査

```
python3 audit.py            # 今月
python3 audit.py 2026/08    # 月指定
```

`~/.codex/sessions/` の rollout ログから `spawn_agent` の実引数を読み、日別にモデル/推論強度の内訳と、明示指定率を出します。
全件が「親を継承」なら、AGENTS.md が読まれていないか、CLI 経由の起動です。

続けて、同じ rollout の `token_usage_record` を親/子・モデル/推論強度ごとに合計した表を出します（単位は千トークン）。「非キャッシュ入力 + 出力」が使用上限の消費に近い目安です。作成者の 2026年9月1〜5日の実測では、親（sol/ultra）の非キャッシュ入力が子の全モデル合計を上回っており、上限を食うのは子の昇格より親の思考分でした。親の推論強度を下げても委譲率が落ちないことは3サンプルずつで確認したので、親は medium で運用しています。

## 補足

- `ROUTING.md` は約45行です。AGENTS.md は長くなるほど1規則あたりの遵守率が下がるので、全体を100行程度に抑えることを勧めます。
- 2026-09-05 の改定（v1.4）で「体制」節と「推論強度の選択基準」表を追加し、運用ルール6の (a)(b) を「terra での推論強度先行の再試行は sol の利用枠を消費しない」に改めました。改定文言は Codex 自身に2巡検収させ、全5項目 PASS を確認しています。
- 同日の v1.5 で2文を追加しました。①再現手順の無い検収 FAIL は成果物の FAIL ではなく検収の不備として扱い、実装側の再試行を起動せず同条件で検収だけをやり直す（sol の利用枠には算入しない）。②sol の利用枠を使い切っても FAIL が残る場合は打ち切り、未解決項目と証跡と試した経路をユーザーへ報告する。背景は実走プローブで、理由の無い FAIL に対して再実装が2回空振りした実測です。こちらも Codex 2巡検収で PASS。
- 遵守状況は rollout ログが唯一の一次資料です。hook での強制は Codex 側の trust 承認が必要で、未承認の hook は無音で飛ばされます。
